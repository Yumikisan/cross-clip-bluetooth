# CBB 二层加密 · 架构分层与信任边界

> 版本：2.2.1　|　适用：Windows（.NET 9 / WPF）· Android（Kotlin / Compose / 澎湃 OS）
> 本文回答一个问题：**蓝牙配对成功到底保护了什么、没保护什么，以及 CBB 在它上面又补了什么。**

---

## 1. 为什么"配对成功"不等于"业务可信"

经典蓝牙 RFCOMM/SPP 的链路加密（Link Key + E0/SAFER+ 之类）由**基带控制器**在射频层完成：

- 加密密钥在**芯片内部**协商与保存，应用层拿不到、读不出、改不了，也无法查询它到底有没有开启；
- 它保护的是**这一跳空口**，语义是"两台设备之间"的通道，不是"这两个 App 之间"的会话；
- 它**没有应用身份**：同一台电脑上任何拿到串口权限的程序，连上去就是"合法的对端"；
- 它**没有防重放**：同一段字节重发一次，接收方无从判断这是新的还是旧的；
- 它**没有会话密钥**：一次配对密钥长期复用，跨天、跨月、跨重装；
- 更实际的问题是：**配对可以只做一次**（Just Works 简化配对甚至无 PIN），之后谁连上都算"配对过"。

一句话：链路加密给的是**空的管道**，CBB 需要的是**只有两个人能用的管道**。管道是谁挖的、挖得多结实，跟"另一个人是不是他本人"完全无关。

结论：蓝牙链路加密只能当作"额外一层"，不能当作唯一保障。CBB 在它之上独立实现**应用层（二层）加密**，自己管密钥、自己验身份、自己防重放。

## 2. 分层视图

```
┌──────────────────────────────────────────────────────────────────────┐
│  L5  业务层（完全无感知）                                              │
│      Windows: Services/BluetoothLinkManager.cs → Wire.cs → 剪贴板同步  │
│      Android: bluetooth/BluetoothService.kt → BtLink → handleFrame    │
│      它只认识「一行一条 JSON」，不知道下面有没有加密                    │
├──────────────────────────────────────────────────────────────────────┤
│  L4  安全层 SecureChannel  ← 本次新增，唯一新增的中间层                │
│      ├─ 协商：探针行 / 二进制帧判定（兼容 2.1.x）                      │
│      ├─ 握手：PSK 挑战-应答（HELLO / CHALLENGE / CONFIRM / ACCEPT）   │
│      ├─ 密钥派生：PBKDF2 → PSK → master → i2r / r2i（双向独立）        │
│      ├─ 加密：AES-256-GCM，每帧随机 96-bit nonce，帧头作 AAD          │
│      ├─ 完整性：128-bit tag，校验失败即丢弃、不向上层递字节            │
│      ├─ 防重放：seq 单调 + 64 位滑动窗口 + 64 条 nonce 去重            │
│      └─ 生命周期：SPP 断开即焚毁会话，重连必须重新握手                 │
├──────────────────────────────────────────────────────────────────────┤
│  L3  传输抽象 ISecureTransport / SecureTransport                     │
│      read(buf,off,len) / write(buf,off,len) / close / isOpen / label │
│      当前实现：RfcommTransport（按 4 KiB 切片写 + flush）             │
│      未来实现：BleGattTransport / LanSocketTransport（见文档 05）      │
├──────────────────────────────────────────────────────────────────────┤
│  L2  经典蓝牙 SPP / RFCOMM 字节流                                     │
│      UUID 8ce255c0-200a-11e0-ac64-0800200c9a66                        │
│      特性：有序、可靠、无消息边界（流）、可被系统静默断开               │
├──────────────────────────────────────────────────────────────────────┤
│  L1  蓝牙基带链路加密（Link Key）—— 芯片负责，App 不可见不可控         │
└──────────────────────────────────────────────────────────────────────┘
```

**关键约束**：L4 只依赖 L3 的五个方法。想把 RFCOMM 换成 BLE GATT 或 Wi-Fi 直连，只写一个新的 L3 实现即可，L4/L5 一行不用改。这条是本次架构设计的硬性要求，也是文档 05 的前提。

## 3. 职责切分：谁负责什么

| 安全属性 | 谁负责 | 说明 |
|---|---|---|
| 空口窃听防护 | L1 基带（+ L4 兜底） | L1 不开也能用，L4 的 GCM 已经覆盖内容机密性 |
| 对端身份核验 | **L4（PSK 挑战-应答）** | L1 只能证明"配对过"，L4 证明"知道口令" |
| 内容机密性 | **L4（AES-256-GCM）** | 即使 L1 明文传输，抓包也拿不到内容 |
| 内容完整性 | **L4（GCM tag + 帧头 AAD）** | 任何一字节被改，tag 必然不匹配 |
| 防重放 | **L4（seq 窗口 + nonce 去重）** | L1 完全没有这个能力 |
| 防降级 | **L4（加密会话内出现明文帧 → 断开）** | 攻击者剥掉加密位无法注入 |
| 密钥生命周期 | **L4（会话级密钥，断开即焚）** | 长期密钥（PSK）永不上线传输 |
| 抗离线爆破 | **L4（PBKDF2 6 万次 + 32 字节 nonce 盐）** | 抓到握手也不能低成本字典攻击 |

## 4. 威胁模型

### 4.1 覆盖的威胁

| 编号 | 威胁 | 攻击者能力 | CBB 的应对 |
|---|---|---|---|
| T1 | 空口嗅探 | 被动抓 RFCOMM 字节流 | GCM 加密，抓到的只有密文与 16 字节帧头 |
| T2 | 中间人改包 | 可篡改任意字节 | tag 校验失败即丢弃；连续 8 次失败断开链路 |
| T3 | 重放旧剪贴板 | 录制后重发 | seq 单调 + 64 帧滑动窗口 + nonce 去重，重复帧丢弃 |
| T4 | 伪造对端 | 能连上 SPP，但不知道口令 | 挑战-应答失败 → 主动 REJECT 并断开 |
| T5 | 降级到明文 | 剥掉 flags 加密位 | 已加密会话中出现明文 DATA 帧 → `plaintext-downgrade` 立即断开 |
| T6 | 密钥外泄（存储） | 拿到设备文件系统 | Windows DPAPI / Android KeyStore 包裹，落盘的不是明文口令 |
| T7 | 半开连接挂死 | 只连不握手 | 12 秒握手超时，超时即断开并上报 |
| T8 | 粘包/半包错位 | 网络层任意切片 | 长度前缀 + 累积缓冲，与 TCP 同级容错（文档 02 §7） |

### 4.2 明确不覆盖的威胁（写清楚，避免误判安全等级）

| 编号 | 威胁 | 为什么不管 | 建议 |
|---|---|---|---|
| N1 | 设备已被完全控制（root / 管理员权限） | 攻击者能读进程内存与 PSK 原文，任何纯软件方案都挡不住 | 依赖操作系统账户隔离与设备锁 |
| N2 | 用户把 PSK 写在便签上 | 人的问题 | 口令强度提示 + 指纹核对 |
| N3 | 首次配置时 PSK 被肩窥 | 带外通道的固有风险 | 用"口令指纹"两端对照（设置页可见 SHA-256 前 3 字节，6 位十六进制） |
| N4 | 拒绝服务（疯狂连接 / 疯狂发帧） | 二层加密不做流量整形 | 连接数上限、握手超时、tag 失败阈值已限制影响面 |
| N5 | 剪贴板内容本身敏感（密码、验证码） | 属于产品策略，不属于传输安全 | 后续可加"敏感内容不自动同步"策略 |
| N6 | 时间侧信道 | GCM 与 HMAC 实现为常数时间；比较用固定时间比较 | 不引入可变时间分支 |

## 5. 密钥体系

```
用户输入口令 passphrase（≥12 字符，两端手抄一致，永不上线）
        │
        │  盐 = nonceC ‖ nonceS（两端各自随机会话，64 字节）
        │  迭代 = HELLO 中声明，10 000 ≤ N ≤ 500 000，默认 60 000
        ▼
   PSK = PBKDF2-HMAC-SHA256(passphrase, salt, N, 32B)      ← 每会话不同
        │
        ├── master = HMAC-SHA256(PSK, "CBB-MASTER-v1" ‖ nonceC ‖ nonceS)
        │        │
        │        ├── kI2R = HMAC-SHA256(master, "CBB-KEY-I2R-v1" ‖ 0x01)   ← 发起端→接收端
        │        └── kR2I = HMAC-SHA256(master, "CBB-KEY-R2I-v1" ‖ 0x01)   ← 接收端→发起端
        │
        └── 握手 MAC 也用 PSK：
            MAC(label) = HMAC-SHA256(PSK, label ‖ nodeInit ‖ 0x00 ‖ nodeResp ‖ nonceC ‖ nonceS)
```

设计要点：

1. **PSK 不等于口令**。口令经 PBKDF2 后才是 PSK，盐是双方随机 nonce 拼接，所以**每次连接的 PSK 都不同**——即使口令被复用，跨会话也没有可比对的重放目标。
2. **双向密钥独立**。i2r 与 r2i 由 domain separation 标签派生，一端加密用的密钥另一端永远不用来加密，杜绝反射攻击与 nonce 空间交叉。
3. **标签绑定身份与随机数**。握手 MAC 里带 `nodeInit`/`nodeResp`（设备 node id）与双方 nonce，交换顺序、角色、会话都被钉死。
4. **长期密钥零传输**。口令与 PSK 从不写成帧、不出本机内存；只有 HMAC 摘要和密文过线。

### 5.1 口令契约（跨端不变量，改之前先看这里）

两端对"用户输入的那串字符"必须做**逐字节相同**的规范化，否则两个人填了同一个口令仍会在 CHALLENGE 阶段判 `psk-mismatch`：

| 规则 | Windows | Android | 说明 |
|---|---|---|---|
| 去空格与 `-` | `PskVault.Normalize` | `SecurityPolicy.normalize` | `ABCD-EFGH` 与 `ABCDEFGH` 视为同一串；生成密钥的分组横线因此可打可不打 |
| 不做大小写折叠 | ✅ | ✅ | 口令保持大小写敏感，靠指纹核对而不是靠猜测 |
| 最小长度 | `SettingsViewModel.MinPskLength = 12` | `SecurityPolicy.MIN_PASSPHRASE_LENGTH = 12` | 生成密钥是 16 位，天然满足 |
| 规范化时机 | 保存时 + `SecurityPolicy` 构造时 | `SettingsPreferences.setPsk` + `SecurityPolicy` 构造时 | 两处都过，避免历史配置绕过 |
| 指纹 | SHA-256 前 **3 字节 / 6 位 hex** | 同 | 只用于两端对照，反推不出口令 |

生成密钥的格式（首次启动向导用）也属于契约：Crockford base32 字母表 `0123456789ABCDEFGHJKMNPQRSTVWXYZ`（去掉 I/L/O/U），16 位 = **80 bit**，显示为 `XXXX-XXXX-XXXX-XXXX`。两端各自实现，靠自检项 `wizard-generated-key` 锁死长度、分组、字母表与唯一性。

## 6. 会话生命周期

```
SPP accept/connect
      ↓
[Negotiating]  发探针行 {"type":"cbb_sec","v":3,"cap":1}
      ├─ 对端回同样一行 → 进入二进制帧，[Handshaking]
      └─ 对端回别的（旧版 JSON）→ [Ready] 走明文行协议（2.1.x 兼容）
                                    └─ Require 模式 → 直接 [Failed] 断开
      ↓
[Handshaking]  HELLO → CHALLENGE → CONFIRM → ACCEPT，限时 12 秒
      ↓
[Ready]        双向 GCM 数据帧；帧号单调递增；重放窗口生效
      ↓
物理断开 / 超时 / 校验失败 / 主动关闭
      ↓
[Closed]       会话密钥、nonce 队列、序号、窗口位图全部丢弃
      ↓
重连 = 全新 SecureChannel 对象 = 必须重新握手（不存在"恢复旧会话"路径）
```

**不做密钥复用是刻意设计**：RFCOMM 断开后重连，`SecureChannel` 是新建对象，`_nonceC/_nonceS/_keyTx/_keyRx` 从 null 开始。即使同一对设备在 1 秒内重连 100 次，也会产生 100 组完全不同的密钥。

## 7. 三类安全模式

| 模式 | 含义 | 无 PSK 时行为 | 对端为 2.1.x 时行为 |
|---|---|---|---|
| `off` | 完全关闭二层加密 | 明文行协议 | 明文行协议 |
| `auto`（默认） | 有 PSK 就加密，没有明文 | 明文行协议 | 明文行协议 |
| `require` | 必须加密 | **拒绝连接**（`no-psk`） | **拒绝连接**（`peer-legacy`） |

选型建议：个人自用选 `auto`；企业/公用机器选 `require`，宁可不连也不降级。

## 9. 自检与验证入口

| 端 | 命令 | 期望 |
|---|---|---|
| Windows | `CBB.exe --selftest` 或 `CBB.exe --selftest D:\report.txt` | 17/17 passed |
| Android | 设置 → 安全 → 运行安全自检 | 17/17 通过 |
| Android（CI/命令行） | `gradle :app:testDebugUnitTest` | tests=2, failures=0 |

自检覆盖：握手+双向数据、错口令拒绝、篡改拒绝、重放拒绝、无密钥明文、require 无密钥拒绝、逐字节切片容错、旧版对端回退、重放窗口边界、EOF 时释放传输、密钥派生 KAT、AES-GCM KAT、真实 TCP 双端明文/加密互通、跨语言握手 KAT、`require` 自愈、生成密钥格式与归一化。

> 自检写入的是 `selftest-security.log`，不是真实链路的 `security.log`：自检会**故意**握手失败，
> 那些行与真机故障长得一模一样，混在一起会让人误判。

> `gradle :app:testDebugUnitTest` 会跑仓库里**全部**单元测试。其中 `BluetoothServiceTest` / `MainActivityTest`
> 是上游 Robolectric 用例，2.1.0 改了行为（`onResume` 也刷新已配对列表、监听自愈会二次 `listen`）后一直红着，
> 与本安全层无关；判定安全层只需看 `security.SecuritySelfTestTest` 两项是否 0 失败。
