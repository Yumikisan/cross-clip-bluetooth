# CBB 二进制帧协议规范（v1 · 冻结）

> 状态：**FROZEN**。字段布局一经发布不得修改，只能通过新增 type / 新增 version 扩展。
> 两端实现：`clipsync-windows/Security/CbbFrame.cs`、`clipsync-android/.../security/CbbFrame.kt`
> 任何改动都必须同时落在两端，并通过文档 04 §5 的 KAT 与自检。

---

## 1. 设计目标

| 目标 | 做法 |
|---|---|
| 跨端严格对齐 | 定长头 + 小端整数 + 显式长度前缀，无对齐填充、无平台相关类型 |
| 抗粘包/半包 | 头里自带 bodyLen，接收方按长度累积，不对流做任何假设 |
| 抗篡改 | 头整体作为 GCM AAD，改一位就废一帧 |
| 可扩展 | flags 有 7 个空闲位，type 有 250 个空号，version 独立 |
| 零拷贝友好 | 头 16 字节可栈上构造，body 可直接从环形缓冲切片 |

---

## 2. 帧头（16 字节，固定）

| 偏移 | 长度 | 字段 | 类型 | 取值 / 说明 |
|---|---|---|---|---|
| 0 | 2 | `magic` | u8[2] | `0x43 0x42`，即 ASCII `'C','B'`。用于在协商阶段识别"对端说的是二进制协议" |
| 2 | 1 | `version` | u8 | 当前恒为 `1`。不等于 1 → `bad-header` 断开 |
| 3 | 1 | `type` | u8 | 见 §3 |
| 4 | 1 | `flags` | u8 | bit0 `0x01` = body 被 AES-GCM 保护；bit1..7 保留为 0 |
| 5 | 1 | `reserved` | u8 | 必须为 0 |
| 6 | 2 | `reserved` | u8[2] | 必须为 0（为将来对齐预留，接收方忽略其值） |
| 8 | 4 | `seq` | u32 LE | 数据帧帧号，从 1 单调递增；握手帧填 0 |
| 12 | 4 | `bodyLen` | u32 LE | body 字节数，`≤ 12 × 1024 × 1024` |

**整帧长度 = 16 + bodyLen。**

### 2.1 为什么 seq 放在第 8 字节

第 5–7 字节是 3 个保留字节，正好把 `seq` 对齐到 8，`bodyLen` 对齐到 12——两端都可以用 `BinaryPrimitives.ReadUInt32LittleEndian(header, 8)` / `ByteBuffer.getInt(8)` 直接读，无需手工拼字节。

### 2.2 头即 AAD

GCM 加密时把**完整 16 字节头**（对端实际收到的字节，不是重新编码的字节）作为 additional authenticated data。这意味着：

- 改 `seq` → tag 失败；
- 改 `type` → tag 失败；
- 把加密位从 1 改成 0 → 帧进不了"明文分支"就已经在 `AcceptSequence` 之后被 `plaintext-downgrade` 拦下；
- 改 `bodyLen` → 帧根本拼不完整，或者拼出来 tag 必炸。

## 3. 帧类型

| type | 名称 | 方向 | body 加密 | 说明 |
|---|---|---|---|---|
| 1 | `HS_HELLO` | 发起端 → 接收端 | 否 | 宣告套件、KDF 迭代数、发起端 nonce、发起端 node id |
| 2 | `HS_CHALLENGE` | 接收端 → 发起端 | 否 | 回传接收端 nonce、接收端 node id、应答 MAC |
| 3 | `HS_CONFIRM` | 发起端 → 接收端 | 否 | 发起端确认 MAC |
| 4 | `HS_ACCEPT` | 接收端 → 发起端 | 否 | 明文套件下接受连接，body 为空 |
| 5 | `HS_REJECT` | 双向 | 否 | 拒绝/失败，携带错误码与原因 |
| 6 | `DATA` | 双向 | 是（加密会话中） | 一条应用层载荷 |

握手帧的 `flags` 恒为 `0`、`seq` 恒为 `0`。收到 `HS_*` 时忽略这两个字段。

type > 6 的情况：**记录日志后丢弃并继续读下一帧**（前向兼容，见 §9）。

---

## 4. 各帧 body 布局

约定：`u8/u16/u32` 均为小端；`node` 为 UTF-8 编码的设备标识，长度 ≤ 255；`nC` = 发起端 nonce（32 B），`nS` = 接收端 nonce（32 B）；`‖` 表示字节拼接。

### 4.1 HS_HELLO（type=1）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `suite` | `0` = 明文套件；`1` = AES-256-GCM 套件 |
| 1 | 4 | `kdfIterations` | u32 LE。suite=0 时为 0；suite=1 时为 PBKDF2 迭代数 |
| 5 | 32 | `nC` | 发起端随机 nonce。suite=0 时全 0 |
| 37 | 1 | `nodeLen` | 发起端 node id 字节数 |
| 38 | nodeLen | `nodeInit` | 发起端 node id（UTF-8） |

`bodyLen = 38 + nodeLen`。

### 4.2 HS_CHALLENGE（type=2）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 32 | `nS` | 接收端随机 nonce |
| 32 | 1 | `nodeLen` | 接收端 node id 字节数 |
| 33 | nodeLen | `nodeResp` | 接收端 node id（UTF-8） |
| 33+nodeLen | 32 | `macReply` | 见 §5 的 `MAC("CBB-HS-REPLY-v1")` |

`bodyLen = 33 + nodeLen + 32`，即 `65 + nodeLen`。

> 接收端 node id 必须随 CHALLENGE 一起下发：发起端要在自己的 MAC 输入里绑定同一个 `nodeResp`，否则两端签的是不同字符串，正确口令也会判为 `psk-mismatch`。（2.2.0 开发期踩过的坑，已修复。）

### 4.3 HS_CONFIRM（type=3）

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 32 | `macConfirm` = `MAC("CBB-HS-CONFIRM-v1")` |

### 4.4 HS_ACCEPT（type=4）

`bodyLen = 0`。

### 4.5 HS_REJECT（type=5）

| 偏移 | 长度 | 字段 | 说明 |
|---|---|---|---|
| 0 | 1 | `code` | 见 §6 |
| 1 | 2 | `reasonLen` | u16 LE，reason 字节数，可为 0 |
| 3 | reasonLen | `reason` | UTF-8，如 `psk-mismatch` |

### 4.6 DATA（type=6）

**加密（flags.bit0 = 1）时：**

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | 12 | `nonce` | 每帧独立随机，**禁止复用** |
| 12 | n | `ciphertext` | AES-256-GCM 输出，n = 明文长度 |
| 12+n | 16 | `tag` | GCM 认证标签 |

`bodyLen = 12 + n + 16 = 28 + n`。AAD = 帧头 16 字节。

**明文（flags.bit0 = 0，仅 `off`/`auto` 无密钥、或对端 legacy 时出现）时：**

| 偏移 | 长度 | 字段 |
|---|---|---|
| 0 | n | `payload` | 原始应用层载荷 |

`bodyLen = n`。已加密会话中出现这种帧 → `plaintext-downgrade`，立即断开（防降级）。

### 4.7 载荷边界

**一帧 = 一条应用层消息 = 一条 JSON（不含结尾 `\n`）**。上层 `Wire.SerializeBody()` / `BtLink.send()` 已保证不带换行；接收侧 `SecureChannel.Read()` 返回 `byte[]`，由上层自行 UTF-8 解码后 `Wire.TryParse`。

## 5. 握手 MAC 的输入构造

两端必须逐字节一致，否则正确口令也会失败。

```
MAC(label) = HMAC-SHA256( PSK,
                ASCII(label)
             ‖ UTF8(nodeInitiator)
             ‖ 0x00                      ← 分隔符，防 "ab"+"c" 与 "a"+"bc" 歧义
             ‖ UTF8(nodeResponder)
             ‖ nC                        ← 32 B
             ‖ nS )                      ← 32 B
```

label 取值：
- 接收端应答：`CBB-HS-REPLY-v1`
- 发起端确认：`CBB-HS-CONFIRM-v1`

其中 `PSK = PBKDF2-HMAC-SHA256(UTF8(passphrase), nC ‖ nS, kdfIterations, 32)`。

会话密钥派生（握手成功后立即执行，不再走网络）：

```
master = HMAC-SHA256(PSK, ASCII("CBB-MASTER-v1") ‖ nC ‖ nS)
kI2R   = HMAC-SHA256(master, ASCII("CBB-KEY-I2R-v1") ‖ 0x01)
kR2I   = HMAC-SHA256(master, ASCII("CBB-KEY-R2I-v1") ‖ 0x01)

发起端：tx = kI2R, rx = kR2I
接收端：tx = kR2I, rx = kI2R
```

## 6. 拒绝码

| code | 名称 | 触发条件 | 对端处置 |
|---|---|---|---|
| 1 | `psk-mismatch` | 任一步 MAC 比对失败 | 两端都 `Failed`，断开，UI 报"密钥不匹配" |
| 2 | `no-psk` | 收到 suite=1 但本端没配 PSK | 断开并提示配置口令 |
| 3 | `unsupported-suite` | suite ∉ {0,1} | 断开 |
| 4 | `plaintext-refused` | 对端提议明文但本端为 `require` | 断开 |
| 7 | `bad-hello` | HELLO body 长度自相矛盾 | 断开 |

> code 5、6 空号保留给将来（如 `cert-untrusted`、`clock-skew`）。

## 7. 粘包 / 半包 / 断续的容错

RFCOMM 是**字节流**，没有消息边界。接收侧统一按下列状态推进：

```
循环：
  if 可用字节 < 16: 继续读（累积），缓冲上限 = 16 + 12MiB + 16
  读 16 字节头 → 校验 magic / version / bodyLen ≤ MaxBody
    失败 → Fail("bad-header")，断开（流已错位，不可能自愈）
  等待 16 + bodyLen 个字节到齐（可能跨多次 read）
  取出整帧 → 处理
```

实现要点（两端同构）：

| 机制 | Windows | Android | 作用 |
|---|---|---|---|
| 累积缓冲 | `_buf/_off/_cnt` | `buf/start/end` | 支持任意切分 |
| 读满自动扩容 | `Ensure()` 倍增到 `HeaderLen+MaxBody+16` | 同 | 大帧不被切死 |
| 尾部压缩 | `Compact()` | 同 | 防止缓冲无限增长 |
| 单次 read 剩余量 | `Read(_buf, _cnt, _buf.Length-_cnt)` | 同 | 不做"一帧一次 read"的假设 |
| 逐字节切片 | 自检项 `byte-fragmentation` | 同 | 每 1 字节一次 write 也必须还原 |

**允许丢帧吗？** 不允许丢"半个"——要么完整解析并验 tag，要么整帧丢弃并记录。TCP/RFCOMM 本身不丢字节，出现字节丢失说明流已损坏，`bad-header` 是正确反应。

## 8. 传输层写入约定

| 约定 | 值 | 原因 |
|---|---|---|
| 单次写上限 | 4 KiB | 避开部分 Android 蓝牙栈 / 部分 PC 适配器的单包上限 |
| 大帧处理 | 循环切片写完再 `flush` | 接收端靠长度前缀重组，无需发送端配合 |
| 并发 | 发送侧全局加锁（`_writeLock`） | 保证不同帧的字节不交错 |
| 握手期写入 | 入队（≤256 条），Ready 后按序 flush | 上层不必等握手完成 |

> 256 条队列上限是防御性的：防止上层在握手失败前把内存灌满。超限则 `Write` 返回 `false`。

## 9. 扩展规则（前向兼容）

| 想做的事 | 正确做法 | 禁止做法 |
|---|---|---|
| 加一种新帧（如心跳、压缩协商） | 分配新的 `type` 号（≥7）。旧端会"记录+丢弃+继续" | 改现有 type 的 body 布局 |
| 加一个 flag（如"压缩") | 用 `flags` 的 bit1..bit7，旧端忽略未知位 | 复用 bit0 的语义 |
| 换算法套件 | HELLO 的 suite 字段加新值（2=国密、3=PQ 混合…）。旧端 `unsupported-suite` 拒绝 | 在 suite=1 内部偷偷换算法 |
| 不兼容的大改 | `version` 升到 2，靠探针行/头的 version 分流 | 改 v1 的字段顺序 |
| 超大载荷（>12 MiB） | 上层分片成多条 DATA | 抬高 MaxBody（会让单帧缓冲失控） |

**保留字段处理**：`header[5]` 必须写 0；`header[6..8]` 写 0 但接收方不得因其非 0 而断开（只记录）。

## 10. 字节示例

### 10.1 探针行（协商第 0 步）

```
7B 22 74 79 70 65 22 3A 22 63 62 62 5F 73 65 63   {"type":"cbb_sec
22 2C 22 76 22 3A 33 2C 22 63 61 70 22 3A 31 7D   ,"v":3,"cap":1}
0A                                                \n
```

对端回同样一行 → 双方切二进制帧。对端回别的 JSON（2.1.x 的鉴权帧）→ 判 legacy，走明文行协议。

### 10.2 HS_HELLO（suite=1，kdf=60000，node="pc-7f3a2b1c"）

```
头：43 42 01 01 00 00 00 00 | 00 00 00 00 | 31 00 00 00
    magic   ver type flags rsv  rsv  | seq=0      | bodyLen=49
体：01                          suite=1
    60 EA 00 00                 kdf=60000 (0xEA60) LE
    00 11 22 33 ... EE FF       nC (32 B 随机)
    0B                          nodeLen=11
    70 63 2D 37 66 33 61 32 62 31 63   "pc-7f3a2b1c"
```

整帧 65 字节。

### 10.3 DATA（加密，明文 18 字节）

```
头：43 42 01 06 01 00 00 00 | 01 00 00 00 | 2E 00 00 00
    magic   ver type flags  | seq=1       | bodyLen=46 = 12+18+16
体：<12B nonce> <18B ciphertext> <16B tag>
```

整帧 62 字节。

## 11. 接收侧决策树（等价伪码）

```
on_frame(type, flags, seq, body):
  HS_HELLO     → 仅接收端处理；发起端收到即 unexpected-hello（断开）
  HS_CHALLENGE → 仅发起端处理；接收端收到即 unexpected-challenge（断开）
  HS_CONFIRM   → 仅接收端处理；发起端收到即 unexpected-confirm（断开）
  HS_ACCEPT    → 仅发起端处理；接收端收到即 unexpected-accept（断开）
  HS_REJECT    → 读 code+reason → Failed("peer-reject:code:reason")
  DATA         → if !AcceptSequence(seq): drop（重放/越窗，不计失败）
                 if flags.bit0==0:
                     if 会话已加密: Fail("plaintext-downgrade")
                     else: 直接上行
                 else:
                     if 无 rxKey: Fail("unexpected-encrypted")
                     if body < 28: Fail("short-data-frame")
                     if nonce 在最近 64 条里出现过: Fail("nonce-reuse")
                     if GCM 解密失败: tagFailures++; if ≥8 Fail("tag-failures"); drop
                     else: 上行明文
  其他          → 记录，丢弃，继续
```

## 12. 与旧协议（2.1.x）的共存

| 场景 | 行为 |
|---|---|
| 2.2 ↔ 2.2 | 探针行互换 → 二进制帧 + 加密 |
| 2.2 ↔ 2.1（`auto`） | 探针行被 2.1 当成一行 JSON 丢掉或报错，2.1 随后发自己的鉴权 JSON → 2.2 判 legacy，改用 `\n` 分隔行协议明文通信 |
| 2.2 ↔ 2.1（`require`） | 同上判 legacy 后立即 `Fail("peer-legacy")` 断开，UI 提示需升级对端 |
| 2.1 ↔ 2.1 | 完全不受影响 |

legacy 模式下 `SecureChannel` 退化为"行切分器"，行为与 2.1 的 `LineReader` 完全一致（含 `\r\n` 兼容、上限 24 MiB）。
