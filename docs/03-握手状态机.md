## 1. 状态定义

用户视角的四态与代码枚举的对应关系：

| 用户语义 | 枚举值 | UI 显示 | 可收发业务数据 | 可继续握手 |
|---|---|---|---|---|
| **未握手** | `Negotiating` | 连接中… | 否（入队） | 是（正在判定协议） |
| **握手中** | `Handshaking` | 正在验证密钥… | 否（入队 ≤256 条） | 是 |
| **加密就绪** | `Ready` | 已连接 · 已加密 / 已连接（明文） | 是 | 否（已终结） |
| **校验失败待断开** | `Failed` | 已断开 · 密钥不匹配 / 已断开 · 安全校验失败 | 否（永久拒绝） | 否 |
| （终态） | `Closed` | — | 否 | 否 |

`Failed` 是"待断开"而不是"已断开"：进入该状态的第一件事就是**主动关闭传输**（`_transport.Close()`），随后由上层读循环收到 null，销毁会话对象。之所以单独一个状态，是为了让失败原因（`FailureReason`）能被 UI 读到——如果直接跳到 `Closed`，上层只能看到"断开了"，无法区分"对端口令错"和"用户拔了蓝牙"。

`Ready` 之下还有三个正交子态，用两个布尔表达：

| 子态 | `IsEncrypted` | `IsLegacy` | 出现条件 |
|---|---|---|---|
| 加密就绪（正常路径） | `true` | `false` | suite=1 握手成功 |
| 明文就绪（策略允许） | `false` | `false` | suite=0 被接受 |
| 明文就绪（旧版对端） | `false` | `true` | 探针协商判定 legacy |

## 2. 状态转移总表

| 当前 | 事件 | 下一状态 | 副作用 |
|---|---|---|---|
| `Negotiating` | 首次 `Read()` | `Negotiating` | 发探针行（只发一次，`_probeStage=1`） |
| `Negotiating` | 收到 magic `C B` | `Handshaking` | 记 `_handshakeStartedAt`；`require` 无密钥则直接 `Failed("no-psk")`；发起端发 HELLO |
| `Negotiating` | 收到探针行原文 | `Handshaking` | 同上（对端先发我们后发，仍能对齐） |
| `Negotiating` | 收到其他行 / 超 64 KiB 垃圾 | `Ready`（legacy） / `Failed` | 判 legacy 后 `require` 模式 → `Failed("peer-legacy")` |
| `Handshaking` | `HS_HELLO` 且本端为接收端 | `Handshaking` | 生成 nS、派生 PSK、回 CHALLENGE、预派生会话密钥 |
| `Handshaking` | `HS_CHALLENGE` 且 MAC 匹配 | `Ready`（加密） | 派生会话密钥、发 CONFIRM |
| `Handshaking` | `HS_CHALLENGE` 且 MAC 不匹配 | `Failed` | 发 `REJECT(1,"psk-mismatch")` 后关闭 |
| `Handshaking` | `HS_CONFIRM` 且 MAC 匹配 | `Ready`（加密） | 接收端完成 |
| `Handshaking` | `HS_CONFIRM` 且 MAC 不匹配 | `Failed` | 发 `REJECT(1,"psk-mismatch")` 后关闭 |
| `Handshaking` | `HS_ACCEPT` | `Ready`（明文） | 仅发起端；suite=0 路径 |
| `Handshaking` | `HS_REJECT` | `Failed` | `FailureReason = peer-reject:code:reason` |
| `Handshaking` | 12 秒未完成（`CheckTimeout`） | `Failed` | `handshake-timeout`，关闭 |
| `Handshaking` | 角色不符的握手帧 | `Failed` | `unexpected-hello/challenge/confirm/accept` |
| `Ready` | `DATA` 正常 | `Ready` | 上行明文载荷 |
| `Ready` | `DATA` 重放/越窗 | `Ready` | 丢弃，**不**判失败（可能是链路重发） |
| `Ready` | `DATA` tag 失败 | `Ready` 或 `Failed` | 计数；累计 ≥ 8 次 → `tag-failures` |
| `Ready` | 加密会话里的明文 DATA | `Failed` | `plaintext-downgrade` |
| `Ready` | nonce 重复 | `Failed` | `nonce-reuse` |
| `Ready` | seq 用尽（`uint.MaxValue`） | `Failed` | `tx-seq-exhausted`（实际不可能达到，防御性） |
| 任意 | 传输异常 / 对端断开 | `Closed` | 读线程返回 null |
| 任意 | `ResetSession()` | `Negotiating` | 清空所有密钥、序号、窗口、队列 |
| 任意 | `Close()` / `Dispose()` | `Closed` | 释放传输（幂等，每个会话只真正关一次） |

## 3. 正常路径（加密）

```
发起端 (initiator, 通常是 PC)              接收端 (responder, 通常是手机)
        │                                          │
        │  ── 探针行 {"type":"cbb_sec","v":3,"cap":1}\n ──▶
        │  ◀── 同样一行 \n ────────────────────────
        │                                          │
 [Handshaking]                                [Handshaking]
        │                                          │
        │  ── HS_HELLO ──────────────────────────▶ │  suite=1, kdf, nC, nodeInit
        │                                          │  派生 PSK = PBKDF2(pw, nC‖nS)
        │  ◀──────────────────────── HS_CHALLENGE ─ │  nS, nodeResp, MAC(REPLY)
        │  PSK = PBKDF2(pw, nC‖nS)                 │  预派生 master/kI2R/kR2I
        │  校验 MAC(REPLY)                          │
        │  派生 master/kI2R/kR2I                    │
        │  ── HS_CONFIRM ────────────────────────▶ │  MAC(CONFIRM)
        │                                          │  校验 MAC(CONFIRM)
 [Ready, encrypted]                          [Ready, encrypted]
        │  ══ DATA(seq=1, GCM) ══════════════════▶ │
        │  ◀══════════════════ DATA(seq=1, GCM) ══ │
```

时序要点：

1. **只有发起端发 HELLO**。角色由"谁是 `accept()` 出来的一方"决定（`isInitiator = !incoming`）。CBB 的链路规则是"只让 PC 拨号，安卓只监听"，所以 PC 恒为发起端。
2. **接收端在发 CHALLENGE 的同时就派生好会话密钥**，因为 `MAC(REPLY)` 需要 PSK，而会话密钥只依赖 PSK + nonce，不依赖后续消息。这样收到 CONFIRM 时只需一次 HMAC 校验即可 `Ready`，省一轮计算。
3. **发起端收到 CHALLENGE 后先验 MAC 再发 CONFIRM**。若 MAC 错了，直接 REJECT，不泄露任何"再试一次"的机会。
4. **`Ready` 之后不再有任何握手帧**。收到 `HS_*` 表示对端状态错乱，按角色不符处理（`unexpected-*`）并断开。

## 4. 明文路径（suite=0）

仅在 `SecurityMode.off`，或 `auto` 且本端未配 PSK、对端也未配 PSK 时出现。

```
发起端                                      接收端
  ── HS_HELLO(suite=0, kdf=0, nC=全0, node) ──▶
                                              若 require → 回 REJECT(4,"plaintext-refused")
  ◀────────────────────────────── HS_ACCEPT ──
[Ready, plaintext]                      [Ready, plaintext]
```

这条路径上仍走二进制帧、仍有 seq 与重放窗口（因为没有密钥，tag 不存在），但不保密、不防篡改。**它的存在意义只有一个：让不想配口令的用户也能用，同时保持帧格式统一，将来打开开关即可无缝变加密。**

## 5. 旧版对端路径（legacy）

```
2.2 端                                     2.1.x 端
  ── 探针行 ─────────────────────────────▶  （不认识，当作一行 JSON 丢掉/报错）
  ◀── {"type":"auth","v":3,...}\n ─────────  2.1 自己的鉴权帧
  ↓
判 legacy：_legacy=true, _state=Ready, IsEncrypted=false
  ├─ mode=auto/off → 该行原样上抛（_stashedLine），后续按 \n 切行 ⇄ 明文互通
  └─ mode=require → Fail("peer-legacy")，断开并提示升级对端
```

`_stashedLine` 的作用：判 legacy 时手里已经吞掉了一行（正是对端的鉴权帧），必须先把它交还给上层，否则上层会一直等一条永远等不到的首帧，表现为"连上了但一直不鉴权"。

## 6. 失败路径与错误码

### 6.1 主动拒绝（本端发出 REJECT 后自行置 Failed）

| 触发 | 发出 | 本端 `FailureReason` |
|---|---|---|
| HELLO 长度自相矛盾 | `REJECT(7,"bad-hello")` | `local-reject:7:bad-hello` |
| suite 不认识 | `REJECT(3,"unsupported-suite")` | `local-reject:3:unsupported-suite` |
| suite=1 但本端无 PSK | `REJECT(2,"no-psk")` | `local-reject:2:no-psk` |
| suite=0 但本端 require | `REJECT(4,"plaintext-refused")` | `local-reject:4:plaintext-refused` |
| MAC 不匹配 | `REJECT(1,"psk-mismatch")` | `local-reject:1:psk-mismatch` |

### 6.2 被动失败（收到对端 REJECT）

`FailureReason = "peer-reject:<code>:<reason>"`，UI 按 code 映射文案：
- `1` → 密钥不匹配，请核对两端口令
- `2` → 对端未配置口令
- `3` → 协议版本不兼容（对端可能更新）
- `4` → 对端要求加密，本端不允许
- `7` → 对端判定本端握手数据异常

### 6.3 本地协议错误（不发帧，直接断）

| `FailureReason` | 含义 |
|---|---|
| `unexpected-hello` / `unexpected-challenge` / `unexpected-confirm` / `unexpected-accept` | 角色不符，帧来得莫名其妙 |
| `bad-challenge` / `bad-confirm` / `no-client-nonce` / `no-session-key` | 帧长或内部状态不对 |
| `no-psk` | `require` 模式且本端无口令 |
| `peer-legacy` | `require` 模式下对端是 2.1.x |
| `probe-garbage` | 协商阶段收到 >64 KiB 且无换行、无 magic 的数据 |
| `handshake-timeout` | 12 秒未完成 |
| `bad-header` | 帧头 magic/version/bodyLen 非法，流已错位 |
| `legacy-frame-too-large` | legacy 行超 24 MiB 仍无换行 |
| `unexpected-encrypted` | 收到加密帧但本端无 rx key |
| `short-data-frame` | 加密 DATA 帧 body < 28 字节 |
| `nonce-reuse` | 最近 64 条内出现过的 nonce |
| `plaintext-downgrade` | 加密会话内出现明文帧 |
| `tag-failures` | 连续累计 8 次 tag 校验失败 |
| `tx-seq-exhausted` | 发送序号达到 u32 上限 |

### 6.4 tag 失败为什么要"累计 8 次"而不是"1 次就断"

单次 tag 失败可能是：链路抖动导致的重组错位、对端刚切换密钥但本端还在旧状态、内存位翻转。一次就断会让正常链路非常脆弱。
但连续 8 次说明"要么密钥不对、要么有人在改包"，此时继续读只是浪费算力，而且会给攻击者提供大量已知明文的 tag 样本。8 次是经验折中，定义为常量可调。

## 7. 超时与并发

| 机制 | 参数 | 驱动者 | 说明 |
|---|---|---|---|
| 握手超时 | 12 秒 | Windows：维护循环（1 秒 tick）`CheckTimeout()`；Android：`authSweepJob` | 防止"连上但不握手"的半开链路一直显示已连接 |
| 写队列上限 | 256 条 | `Write()` | 握手期入队，防上层灌爆内存 |
| 读锁 | 无（单读线程） | 传输读循环 | `Read()` 只允许一个线程调用 |
| 写锁 | `_writeLock` | 任意线程 | 保证帧字节不交错 |
| 队列锁 | `_pendingLock` | 任意线程 | 与写锁分离，避免 flush 时死锁 |

`FlushPending()` 在 `Ready` 之后、**释放 `_pendingLock` 之后**才逐条发送，避免"持锁发网络"造成的长时间阻塞。

### 握手竞态：上层先说话怎么办

真实时序里，`accept()` 返回后业务层立刻会发一条"我是谁/我准备好了"的 JSON，而握手还没开始。`Write()` 在非 `Ready` 状态一律入队，`Ready` 时按入队顺序 flush。上层代码因此完全不需要感知握手存在——这是"业务层无感"的关键实现点。

## 8. 会话重置与重连

```
SecureChannel.ResetSession():
    nC = nS = psk = txKey = rxKey = null
    txSeq = 0; rxStarted = false; rxHighest = 0; rxBitmap = 0
    recentNonces.clear(); tagFailures = 0
    IsEncrypted = false; FailureReason = ""; PeerNode = ""
    legacy = false; stashedLine = null; probeStage = 0
    state = Negotiating
    pending.clear()
```

`ResetSession()` 是为"能在同一个传输对象上重建流"的传输层准备的（如未来 LAN 长连接复用 socket）。当前 RFCOMM 实现不用它：断开就销毁对象，重连就 `new SecureChannel(...)`，**不存在任何跨连接的密钥延续**。

对安全性的意义：**重放窗口、序号、nonce 缓存全部随会话一起消失**。攻击者无法利用"上一会话的序号"在新会话里注入（新会话首帧无条件接受 seq，然后立窗口）。

### 关闭语义（最容易写错的一处）

读线程因**对端正常关闭**返回 `null` 时，内部状态已经是 `Closed`。此时如果 `Close()` 写成像
"`if (state == Closed) return;`"这样提前返回，**传输就永远不会被释放**——socket 一直挂着，安卓上表现为 RFCOMM 通道泄漏，直到进程退出。

正确写法：`Close()` 无条件把状态置 `Closed`，再用一个一次性闸门（`_transportClosed`）保证传输只关一次；
`ResetSession()` 要把闸门复位，否则复位后的会话再也关不掉传输。

## 9. 状态机自检用例

`SecuritySelfTest` 覆盖以下转移（两端同构）：

| 用例 | 覆盖转移 |
|---|---|
| `handshake-and-exchange` | Negotiating → Handshaking → Ready(encrypted)，双向 DATA |
| `wrong-psk` | Handshaking → Failed（`psk-mismatch`），对端收到 `peer-reject:1` |
| `tampered-frame` | Ready 下 tag 失败 → 丢弃，不上行 |
| `replayed-frame` | Ready 下 seq 重复 → 丢弃 |
| `plaintext-without-key` | Handshaking → Ready(plaintext)（suite=0） |
| `require-without-key` | Negotiating → Failed（`no-psk`） |
| `byte-fragmentation` | 逐字节写入仍能握手 + 完成数据交换 |
| `legacy-peer-fallback` | Negotiating → Ready(legacy) |
| `replay-window` | 窗口边界（第 64 帧内接受、超窗拒绝） |
| `transport-closed-on-eof` | 对端 EOF 时 `Close()` 仍释放传输，且幂等（2.2.0 修的真实缺陷） |
| `key-schedule-vectors` | 密钥派生 KAT |
| `aes-gcm-vector` | AES-GCM KAT |
