# 加密算法插拔与替换规范

> 目的：让"换算法"变成**加一个套件 + 加一套 KAT**，而不是重写安全层。
> 本文描述当前实现的可替换点、扩展步骤，以及必须遵守的不变量。

---

## 1. 当前算法参数（唯一权威表）

| 项 | 值 | Windows | Android | 冻结? |
|---|---|---|---|---|
| 主密码学库 | — | `System.Security.Cryptography` | `javax.crypto` + 手写 PBKDF2 | — |
| KDF | PBKDF2-HMAC-SHA256 | `CbbCrypto.Pbkdf2` | `CbbCrypto.pbkdf2` | 随套件 |
| KDF 默认迭代 | 60 000 | `DefaultKdfIterations` | `DEFAULT_KDF_ITERATIONS` | 随套件 |
| KDF 迭代范围 | 10 000 – 500 000 | `Min/MaxKdfIterations` | `MIN/MAX_KDF_ITERATIONS` | 随套件 |
| PSK 长度 | 32 B | `KeyBytes` | `KEY_BYTES` | 随套件 |
| 握手 nonce | 32 B | `HandshakeNonceBytes` | `HANDSHAKE_NONCE_BYTES` | 随套件 |
| 会话密钥派生 | HMAC-SHA256 + domain separation | `DeriveSessionKeys` | `deriveSessionKeys` | 随套件 |

| 数据 nonce | 12 B 随机/帧 | `NonceBytes` | `NONCE_BYTES` | 随套件 |
| 认证标签 | 16 B | `TagBytes` | `TAG_BYTES` | 随套件 |
| AAD | 16 B 帧头 | `FrameCodec.EncodeHeader` | `FrameCodec.encodeHeader` | **协议级，不随套件变** |
| 防重放窗口 | 64 帧 | `SecureChannel.ReplayWindow` | `REPLAY_WINDOW` | 可配置 |
| nonce 去重缓存 | 64 条 | `MaxRecentNonces` | `MAX_RECENT_NONCES` | 可配置 |
| 标签失败阈值 | 8 次 | 字面量 8 | 字面量 8 | 可配置 |
| 握手超时 | 12 s | `HandshakeTimeoutSeconds` | `HANDSHAKE_TIMEOUT_SECONDS` | 可配置 |

**不可替换的三件事**（换了就不是 CBB 协议了）：

1. 16 字节帧头布局；
2. 帧头作 AAD；
3. `probe line → 二进制帧` 的协商方式。

其余全部可替换。

## 2. 套件编号空间

`HS_HELLO.suite` 是一个 u8：

| 值 | 含义 | 状态 |
|---|---|---|
| 0 | 无加密（明文帧） | 已实现 |
| 1 | AES-256-GCM + PBKDF2-SHA256 | 已实现，默认 |
| 2 | 预留：SM4-GCM（国密） | 未实现 |
| 3 | 预留：AES-256-GCM + ML-KEM/ML-DSA 混合（后量子） | 未实现 |
| 4 | 预留：ChaCha20-Poly1305（弱 CPU 备选） | 未实现 |
| 5–127 | 预留 | — |
| 128–255 | 实验/私有（不进入正式兼容矩阵） | — |

协商规则（**必须**照此实现，否则会引入降级漏洞）：

- 发起端只提议**一个**套件，不提议列表。原因：多套件列表会带来"选最低公共"的降级面。
- 接收端不认识该套件 → `REJECT(3,"unsupported-suite")` 断开，**不允许**"那我们就用明文吧"。
- 任何环境下都**不允许**因协商失败而回落到 suite=0——回落必须由本端策略（`SecurityMode.off/auto` 且无密钥）显式决定，且发生在握手之前的 HELLO 生成阶段。

## 3. 可替换点地图

当前实现把算法直接写在 `CbbCrypto`（静态类 / 顶层对象）里。要支持多套件，按下面的最小改动引入套件抽象：

```
SecureChannel
   ├── 只用 4 个原语：derivePsk / handshakeMac / deriveSessionKeys / seal+open
   └── 通过 CbbSuite 接口拿到它们（现在直接调 CbbCrypto 静态方法）
```

### 3.1 目标接口（两端同构）

```csharp
// Windows: Security/ICbbSuite.cs
public interface ICbbSuite
{
    byte Id { get; }                       // 1, 2, 3 ...
    int NonceBytes { get; }                // 12
    int TagBytes { get; }                  // 16
    int DefaultKdfIterations { get; }
    byte[] DerivePsk(string passphrase, byte[] salt, int iterations);
    byte[] Mac(byte[] psk, byte[] data);
    void DeriveSessionKeys(byte[] psk, byte[] nC, byte[] nS,
                           out byte[] tx, out byte[] rx, bool isInitiator);
    byte[] Seal(byte[] key, byte[] nonce, byte[] plain, byte[] aad, out byte[] tag);
    byte[]? Open(byte[] key, byte[] nonce, byte[] cipher, byte[] tag, byte[] aad);
}
```

```kotlin
// Android: security/CbbSuite.kt
interface CbbSuite {
    val id: Byte
    val nonceBytes: Int
    val tagBytes: Int
    val defaultKdfIterations: Int
    fun derivePsk(passphrase: String, salt: ByteArray, iterations: Int): ByteArray
    fun mac(psk: ByteArray, data: ByteArray): ByteArray
    fun deriveSessionKeys(psk: ByteArray, nC: ByteArray, nS: ByteArray,
                          isInitiator: Boolean): Pair<ByteArray, ByteArray> // tx to rx
    fun seal(key: ByteArray, nonce: ByteArray, plain: ByteArray, aad: ByteArray): ByteArray // cipher‖tag
    fun open(key: ByteArray, nonce: ByteArray, cipher: ByteArray, tag: ByteArray, aad: ByteArray): ByteArray?
}
```

### 3.2 引入抽象时必须保持不变的行为

| 不变量 | 说明 |
|---|---|
| MAC 输入拼接顺序 | `label ‖ nodeInit ‖ 0x00 ‖ nodeResp ‖ nC ‖ nS`，见文档 02 §5 |
| domain separation 标签字符串 | `CBB-MASTER-v1` / `CBB-KEY-I2R-v1` / `CBB-KEY-R2I-v1` / `CBB-HS-REPLY-v1` / `CBB-HS-CONFIRM-v1` |
| 双向密钥独立 | i2r ≠ r2i，各自只能用于一个方向 |
| nonce 随机性来源 | 必须来自 OS CSPRNG（`RandomNumberGenerator` / `SecureRandom`），禁止 `Random`/`Math.random` |
| 常数时间比较 | MAC 与 tag 的比对一律定长比较，禁止 `==` / `Arrays.equals` 之外的短路实现 |
| 头作 AAD | AAD 恒为对端收到的 16 字节头 |

## 4. 新增一个套件：完整步骤清单

以"加 suite=2 国密 SM4-GCM"为例。

### 步骤 1：确定密码学参数，写进参数表

| 项 | SM4-GCM 取值 |
|---|---|
| PSK 长度 | 32 B（SM4 用 16 B 密钥；PSK 取前 16 字节或改 KDF 输出长度，需在文档里定死） |
| nonce | 12 B |
| tag | 16 B |
| KDF | PBKDF2-HMAC-SM3（若无标准库则退化为 HMAC-SHA256，需注明并保持两端一致） |

### 步骤 2：两端同时实现原语

- Windows：新增 `Security/Suites/Sm4GcmSuite.cs` 实现 `ICbbSuite`。若无现成 SM4 库，可引入经过审计的第三方实现，**不得自行实现分组密码**。
- Android：新增 `security/suites/Sm4GcmSuite.kt` 实现 `CbbSuite`。

### 步骤 3：注册套件表

```csharp
private static readonly Dictionary<byte, ICbbSuite> Suites = new() {
    [1] = new AesGcmSuite(),
    [2] = new Sm4GcmSuite(),   // 新增
};
```

Android 同构。`SecureChannel` 从 `policy.PreferredSuite` 取发起端套件，从 `Suites[hello.suite]` 取接收端套件。

### 步骤 4：策略层暴露选择

`SecurityPolicy` 增加 `PreferredSuite`（默认 `1`）。UI 只在"高级"里露出，普通用户永远用 1。

### 步骤 5：生成 KAT 向量并**两端各自校验**

KAT 必须用**第三个独立实现**生成，不能用被测代码自己生成（否则测的是自洽性，不是正确性）。当前 suite=1 的向量由 Python `hashlib`/`hmac` 与 Node `crypto` 双份独立生成。

必须固定的向量组：

| 向量 | 输入 | 期望输出 |
|---|---|---|
| `pbkdf2` | passphrase="cbb-test-vector-001", salt=固定 64 B, N=10000 | 32 B 定值 |
| `mac-reply` | 固定 nC/nS/nodeInit/nodeResp | 32 B 定值 |
| `master` | 固定 psk/nC/nS | 32 B 定值 |
| `i2r` / `r2i` | 固定 master | 各 32 B 定值 |
| `aes-gcm` | 固定 key/nonce/aad/明文 | 固定 ciphertext + tag |

新套件必须补齐同结构的 6 组向量，并同时加进两端自检的 `key-schedule-vectors` 与 `aes-gcm-vector` 用例。

### 步骤 6：跨端互操作验证

单端 KAT 通过**不代表**能互通（2.2.0 开发期就踩过：两端 KAT 全绿，但 CHALLENGE 少带 node id + 迭代数不对称，导致正确口令判错）。必须做：

1. 两端各自跑自检 12/12；
2. 真机互连：相同口令 → `已连接 · 已加密`；
3. 故意改一位口令 → 两端都在 1 秒内断开并报密钥不匹配；
4. 抓包确认第一帧是 `43 42 01 01`（HELLO）而不是明文 JSON。

### 步骤 7：更新文档与版本矩阵

- 本文 §2 套件表状态列；
- 文档 02 §9 扩展规则若涉及新 type/flags 也要同步；
- `README-增强说明.md` 兼容性矩阵；
- `ARCHIVE-*.md` 版本矩阵。

## 5. 安全策略开关（可配置项）

以下开关应可通过设置页/配置暴露，但**默认值不得弱化**：

| 开关 | 默认 | 取值范围 | 弱化风险 |
|---|---|---|---|
| `SecurityMode` | `auto` | off / auto / require | `off` = 无任何二层保护 |
| 口令最短长度 | 12 字符 | ≥12（建议不降低） | 短口令易被字典攻击 |
| KDF 迭代 | 60 000 | 10 000 – 500 000（超范围被夹紧） | 低迭代削弱抗爆破 |
| 防重放窗口 | 64 | 16 / 32 / 64 / 128 / 256 | 过小会误杀正常重传 |
| 标签失败阈值 | 8 | 1 – 32 | 过大会放大 DoS 窗口 |
| 握手超时 | 12 s | 5 – 30 s | 过短误杀慢设备 |
| 安全日志 | 开 | 开 / 关 | 关掉会失去事后取证能力 |
| 明文调试日志 | Release 恒关 | 仅 `#if DEBUG` / `BuildConfig.DEBUG` | **不可在 Release 打开** |

`KdfIterations` 的夹紧逻辑在两端都存在（`Math.Clamp` / `coerceIn`），且夹紧发生在**接收端解析 HELLO 时**与**发送端生成 HELLO 前**两处——防止恶意对端用 `iterations=1` 削弱派生强度。

## 6. 后量子迁移路径（预留说明）

若将来引入 ML-KEM（Kyber）做密钥交换，**不要**改动现有 PSK 模型，而是新增 suite=3 走"混合"：

```
suite=3 握手（概念）：
  HELLO    : suite=3 ‖ kdf ‖ nC ‖ nodeInit ‖ ML-KEM 公钥
  CHALLENGE: nS ‖ nodeResp ‖ ML-KEM 密文（encapsulated）‖ MAC(REPLY)
  CONFIRM  : MAC(CONFIRM)

PSK     = PBKDF2(passphrase, nC‖nS)                 ← 保留口令这条腿
KEM     = ML-KEM.Decaps(密文, 私钥) = 共享秘密 S     ← 新增这条腿
master  = HMAC(PSK ‖ S, "CBB-MASTER-v3" ‖ nC ‖ nS)   ← 两腿组合
```

意义：即使将来口令泄露，攻击者仍需破 KEM；即使 KEM 被量子计算机破，仍需口令。这叫"混合"，是过渡期的标准做法。

要求：suite=3 的 HELLO 体长度远超当前固定 38 字节，因此**必须**依赖 `bodyLen` 解析而不是固定长度（现有实现已经是长度驱动，天然支持）。旧端收到 suite=3 会 `REJECT(3,"unsupported-suite")`，行为正确。

## 7. 禁止事项（红线）

| 禁止 | 原因 |
|---|---|
| 固定 IV / 固定 nonce / 计数器复位后复用 | GCM 下 nonce 复用等于直接泄密 + 伪造可行 |
| ECB、CBC 无 MAC、CBC+固定 IV | 无完整性、可重排、可篡改 |
| 自己实现分组密码 / 自己发明 KDF | 侧信道与结构错误概率极高 |
| 把 PSK 或口令以任何形式发到链路上 | 一旦上线即失去"离线预共享"的全部意义 |
| 用蓝牙 Link Key 替代二层加密 | 见文档 01 §1 |
| 用 `==` 比较 MAC | 时序侧信道 |
| 关闭 tag 校验"以提升吞吐" | 等于删除完整性保护 |
| 在 Release 构建输出明文日志 | 日志在 `%APPDATA%` / `sdcard` 可被任意读取 |
| 换算法时不加 KAT | 两端各自"自洽"但互不兼容，症状是莫名 `psk-mismatch` |
