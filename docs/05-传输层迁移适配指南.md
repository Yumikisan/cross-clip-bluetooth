# 传输层迁移适配指南

> 目标：把安全层（L4）与传输层（L3）彻底隔开，使"换蓝牙协议"变成**只写一个适配器**。
> 当前适配器：`RfcommTransport`（经典蓝牙 SPP）。未来候选：BLE GATT、BLE L2CAP/CoC、TCP/UDP-over-LAN、Wi-Fi Direct。

---

## 1. 契约：安全层对传输层的唯一要求

```csharp
// Windows: Security/ISecureTransport.cs
public interface ISecureTransport
{
    int  Read(byte[] buffer, int offset, int count);   // 阻塞；返回读到的字节数；0 或 -1 表示对端关闭
    void Write(byte[] data, int offset, int count);    // 写满 count 字节，或抛异常
    void Close();
    bool IsOpen { get; }
    string PeerLabel { get; }                          // 仅用于日志，绝不作为身份
}
```

```kotlin
// Android: security/SecureTransport.kt
interface SecureTransport {
    fun read(buffer: ByteArray, offset: Int, count: Int): Int   // 阻塞；0/-1 表示关闭
    fun write(data: ByteArray, offset: Int, count: Int)        // 写满或抛异常
    fun close()
    val isOpen: Boolean
    val peerLabel: String
}
```

### 1.1 语义必须严格满足

| 要求 | 说明 | 违反后果 |
|---|---|---|
| **有序** | 写入顺序 = 读出顺序 | 帧错位，`bad-header` |
| **可靠** | 不丢字节、不重复字节 | 同上 |
| **面向字节流** | 一次 `write(8192)` 可能被分成任意多次 `read`，`read` 可能只返回 1 字节 | 若适配器返回"半帧就当整帧"，解析必错 |
| **`Read` 阻塞** | 无数据时阻塞等待，不要返回 0 | 返回 0 会被当成对端关闭，链路被误判断开 |
| **`Read` 可被 `Close` 打断** | 另一线程 `Close()` 后阻塞中的 `Read` 应尽快返回 -1 | 否则断连时读线程挂死，进程无法退出 |
| **`Write` 写满** | 循环写完或抛异常，不允许"部分写成功且不报错" | 半帧上线，对端永远等不齐 |
| **`PeerLabel` 非身份** | 只入日志 | 若用它做鉴权，等于用可伪造的字符串当密码 |

安全层对传输层**没有**其他要求：不要求有连接概念、不要求 QoS、不要求 MTU、不要求回调。这条边界是刻意压薄的。

## 2. 迁移到 BLE GATT 的注意事项

BLE 与 RFCOMM 有本质差异：**GATT 是包模型，不是流模型。** 不能直接把"写一个 characteristic"当成"写一段字节流"。

### 2.1 需要在适配器里补的三件事

| 问题 | 现象 | 适配器要做的事 |
|---|---|---|
| MTU 远小于帧 | 默认 MTU 23 → 有效载荷 20 字节；一帧可能上百字节 | 发：把帧切成 `mtu-3` 的块，逐块 `writeCharacteristic`；收：把通知块拼回连续字节流 |
| 写模式差异 | Write Without Response 快但可能丢；Write With Response 慢但可靠 | **必须用 With Response**（或 L2CAP CoC 的有序模式）。丢一字节 = 整条链路报废 |
| 通知本身也是包 | `onCharacteristicChanged` 每次只给一个包 | 适配器内部维护一个 FIFO 缓冲，`Read()` 从中取字节，空了就阻塞等待下一个通知 |

### 2.2 必须自己实现"假流"

```
GATT 通知包（20~500 B）
   ↓ 入队（BlockingQueue / RingBuffer）
适配器内部连续字节池
   ↓ read(buffer, off, count) 按需切片
SecureChannel 的累积缓冲
```

适配器内部**必须**有一个"字节池 + 条件变量"，不能假设"一个通知 = 一次 read"。这是 BLE 上最容易写错的地方。

### 2.3 会话与重连

BLE 的 `BluetoothGatt` 生命周期比 socket 复杂：`connectGatt` → `discoverServices` → 开通知 → 才能收发。因此：

- `IsOpen` 应在"服务发现完成且通知已开启"后才为 `true`；
- 连接断开事件必须让阻塞中的 `Read()` 返回 -1，否则 `SecureChannel` 永远不知道自己已经死了；
- **每次重连都要新建 `SecureChannel`**，不复用旧对象（GATT 重连后对端可能已经换了设备上下文）。

### 2.4 速率与超时

BLE 有效吞吐远低于 RFCOMM（实测常见 5–50 KB/s，受连接间隔与 MTU 影响）。因此迁移后要重估：

| 参数 | RFCOMM 下 | BLE 下建议 |
|---|---|---|
| 握手超时 | 12 s | 20–30 s（服务发现本身就要 1–3 s） |
| 大剪贴板分片 | 12 MiB 单帧上限足够 | 上层主动切成 ≤64 KiB 的分片，避免长时间占住单帧 |
| 写队列上限 | 256 条 | 64 条（BLE 排空慢，堆太多只会延迟更久） |

这些是**策略参数**，不改协议。

## 3. 迁移到 TCP/UDP-over-LAN 的注意事项

| 项 | TCP | UDP |
|---|---|---|
| 是否满足契约 | 直接满足（本身就是有序可靠字节流） | **不满足**，需在适配器里补序号 + 重传 + 重组，等于自己写一个可靠层 |
| PSK 是否仍必要 | **更必要**（局域网比蓝牙空口更容易被嗅探） | 同 |
| 监听/拨号角色 | 需重新定义"谁连谁"，但**链路层规则（只让一端发起）仍要保留**，双端同时拨号会产生两条链路 | 同 |
| `PeerLabel` | 可用 `IP:port`，但只入日志 | 同 |

**UDP 不建议直接接**：UDP 上要做可靠传输，工作量与风险都超过收益，且失去"零配置直连"的意义。若确需局域网，用 TCP。

## 4. 迁移步骤清单

新增一个传输后端，按顺序做：

1. **实现适配器**（`BleGattTransport` / `TcpTransport`），严格满足 §1.1 的七条。
2. **写单元测试**：模拟"一次 write 被切成 1/3/7 字节随机多次 read"，跑通握手 + 数据交换。可以直接复用自检里的 `PipeTransport` / `Harness` 骨架，把切片策略参数化。
3. **不改任何安全代码**：`SecureChannel`、`CbbCrypto`、`CbbFrame`、`SecurityPolicy` 一行都不许动。如果发现"必须改安全层才能跑通"，说明适配器契约没满足，回去改适配器。
4. **改接入点**：Windows `BluetoothLinkManager.PeerSession` 里把 `new RfcommTransport(...)` 换成新适配器；Android `BtLink` 里把 `RfcommTransport(socket, name)` 换掉。仅此一处。
5. **跑自检**：两端 12/12 必须仍然全绿。
6. **真机互通**：新传输 ↔ 新传输；新传输 ↔ 旧传输（如果协议层能桥接）。
7. **更新本文**：把新适配器的坑写进 §2/§3 对应位置。

### 4.1 接入点在哪（改动面只有两行）

| 端 | 文件 | 位置 |
|---|---|---|
| Windows | `Services/BluetoothLinkManager.cs` | `PeerSession` 构造函数中 `new SecureChannel(new RfcommTransport(_stream, name), ...)` |
| Android | `bluetooth/BtLink.kt` | `val channel = SecureChannel(RfcommTransport(socket, deviceName), ...)` |

## 5. 迁移后的兼容性策略

| 场景 | 建议 |
|---|---|
| 新传输与旧传输必须互通 | 在**上层业务协议**里做桥接，不要试图让 RFCOMM 与 BLE 在二层互转 |
| 双栈并存（推荐） | 同时保留 RFCOMM 与 BLE 适配器，用户可选或自动择优；安全层对两者一视同仁 |
| 渐进上线 | 单独分支（如 `feat/ble-gatt-preview`），**永不合并主线**，避免一次改动同时背两个风险 |

---

## 6. 迁移时的红线

| 禁止 | 原因 |
|---|---|
| 为适配新传输而放宽"有序可靠"的假设 | 帧协议依赖它，放宽即错位 |
| 在适配器里做应用层解析（找 `\n`、认 JSON） | 适配器只管搬字节；解析是 L4 的职责 |
| 用新传输的"消息边界"替代长度前缀 | 一旦换传输或换 MTU 就崩 |
| 因为 BLE 慢就关掉加密 | 慢是吞吐问题，不是安全问题 |
| 复用旧 `SecureChannel` 对象跨连接 | 序号与 nonce 缓存跨会话复用 = 送攻击者一个大礼 |
