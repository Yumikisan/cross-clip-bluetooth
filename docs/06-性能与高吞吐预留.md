# 性能与高吞吐预留

> 结论先行：**当前加密开销不是瓶颈，RFCOMM 才是。** 但要为"将来换成高吞吐链路"留好口子，所以本文把成本模型、可调旋钮、优化路径都写清楚，避免未来在大改时破坏安全属性。

---

## 1. 成本模型（量级参考，需按实测校准）

单次操作的开销量级（x64 带 AES-NI / ARMv8 带 Crypto Extensions）：

| 操作 | 量级 | 触发频率 |
|---|---|---|
| AES-256-GCM 加密或解密 1 KiB | 微秒级（个位数） | 每帧 1 次 |
| HMAC-SHA256 单次 | 微秒级 | 握手 3 次，数据帧 0 次 |
| PBKDF2 60 000 次 | 数十毫秒 | **每连接 1 次**（握手时） |
| 随机 nonce（12 B） | 亚微秒 | 每帧 1 次 |
| 序列检查 + 位图更新 | 纳秒级 | 每帧 1 次 |
| nonce 去重（64 条 HashMap） | 纳秒–微秒级 | 每帧 1 次 |

对比 RFCOMM SPP 的实际吞吐（典型 100–200 KB/s，受蓝牙版本与适配器影响），**加密链路每帧多出的几十微秒完全可以被链路本身掩盖**。这也解释了为什么 2.2.0 没有做任何加密流水线优化：没有必要。

真正需要关注的只有两点：

1. **握手延迟**：PBKDF2 60k 在低端安卓上可能到 100–200 ms。它发生在"连接建立后、首次同步前"，用户感知为"连上后要多等一下"。若将来觉得慢，**不要降低迭代数**，而是：
   - 把派生结果在**会话内**缓存（已由架构保证：一次会话只派生一次）；
   - 或改用内存更友好的 Argon2id（属新套件，见文档 04）。
2. **大剪贴板**：一张 10 MiB 图片会被切成多少帧取决于上层。当前是**单帧承载整块载荷**（上限 12 MiB）。单帧 12 MiB 意味着：
   - 发送侧一次性构造 12 MiB 明文 + 12 MiB 密文 + 16 B 头 ≈ 24 MiB 瞬时内存；
   - 接收侧累积缓冲会增长到 12 MiB + 16 B；
   - GCM 单次 12 MiB 是连续运算，无法与网络重叠。

   这是当前唯一的"性能悬崖"，也是 §3 要预留的改造点。

## 2. 现有缓冲与内存占用

| 缓冲 | 位置 | 上限 | 说明 |
|---|---|---|---|
| 接收累积缓冲 `_buf` | `SecureChannel` | `16 + 12 MiB + 16` | 从 64 KiB 起倍增，尾部有 `Compact()` 回收 |
| 发送入队 `_pending` | `SecureChannel` | 256 条 | 握手期暂存上层消息，`Ready` 后 flush |
| nonce 去重队列 | `SecureChannel` | 64 条 | FIFO + HashSet 双结构，O(1) 查重 |
| 重放位图 | `SecureChannel` | 8 B | 64 位整数，无额外分配 |
| PSK / 会话密钥 | `SecureChannel` | 4 × 32 B | 断开即置 null |

稳态下（1 KiB 消息）每帧分配：头 16 B + nonce 12 B + cipher n B + tag 16 B + body 数组 + 明文数组。**约 4 次小对象分配/帧**。在 100 KB/s 的量级下 GC 压力可忽略；在 MB/s 量级下会成为次要热点，对应 §3.2。

## 3. 预留的优化路径（按优先级）

### 3.1 大载荷分片（最高优先级）

**现状**：一条 10 MiB 消息 = 一帧 10 MiB。

**改造**：在上层（`Wire` / `BtLink`）把超大载荷切成 ≤256 KiB 的分片，每片仍是一条完整 DATA 帧。

**收益**：单帧内存从 24 MiB 降到约 0.5 MiB；GCM 运算可与网络传输重叠；单帧校验失败只丢 256 KiB，不用重传整块。

**代价**：需要在业务层加"分片/重组"逻辑（带 `msgId` + `index` + `total`）。**不要**放进安全层——分片是应用语义，不是安全语义。

**为什么不是现在做**：现有业务（文本/小图）几乎不会触发这个路径，加了反而增加复杂度与出错面。触发条件写清楚即可。

### 3.2 零拷贝与池化

| 优化 | 做法 | 收益 |
|---|---|---|
| `ArrayPool<byte>` / `ByteArrayPool` | 帧缓冲、密文缓冲复用 | 消除每帧 2–4 次分配 |
| `Span<byte>` / `ByteBuffer` 切片 | 避免 `ToArray()` 的中间拷贝 | 少一次全量拷贝 |
| `IBufferWriter` / 分片写 | 头与体分别写，不拼整帧 | 省一次 24 MiB 拼接（大帧场景显著） |
| 直接写 socket/stream | `Seal` 输出直接进传输缓冲 | 省一层拷贝 |

要求在改造后仍然满足：**AAD 必须是实际发出的那 16 字节头**。如果改成"头与体分别写"，AAD 要传"将要写出的头"，不能重新编码一份（虽然当前编码是确定性的，但保持"发什么就验什么"的习惯更安全）。

### 3.3 加密流水线

GCM 单帧是串行的（tag 依赖全部密文），因此**不能**把一帧拆给多线程。能做的是**跨帧流水线**：

```
线程 A：读帧 → 校验 seq → 解密 → 入交付队列
线程 B：从交付队列取 → 业务处理（JSON 解析、剪贴板写入）
```

当前是单线程（`Read()` 在传输读循环里同步处理）。改造要点：解密仍在读线程（保证顺序），只把**业务处理**移到工作线程。这样加密与业务并行，且不破坏顺序保证。

**禁止**：多线程并发解密同一方向的数据帧。seq 窗口与 nonce 缓存不是并发安全的，而且乱序解密会让"重放判定"失效。

### 3.4 硬件加速

两端都应确保使用硬件 AES：

| 端 | 检查方式 | 说明 |
|---|---|---|
| Windows | `AesGcm` 在 .NET 8+ 自动走 AES-NI/PCLMULQDQ | 无需配置 |
| Android | ARMv8 CE（绝大多数 2018 年后设备） | `Cipher.getInstance("AES/GCM/NoPadding")` 由 Conscrypt 走硬件 |

若目标设备无硬件 AES，GCM 会退化为软件实现（数量级变慢）。此时**不要换成弱算法**，而应考虑 ChaCha20-Poly1305（新套件，文档 04 §2 的 suite=4）。

## 4. 可配置的性能旋钮

以下参数应可通过常量/配置调整，**调整不得削弱安全属性**：

| 旋钮 | 当前值 | 可调范围 | 影响 |
|---|---|---|---|
| `MaxBody` | 12 MiB | 64 KiB – 12 MiB | 单帧上限；调小可强制上层分片 |
| 接收缓冲初始大小 | 64 KiB | 4 KiB – 1 MiB | 小帧为主的场景调小更省内存 |
| 发送切片大小 | 4 KiB | 1 KiB – 64 KiB | RFCOMM 上 4 KiB 是安全值；TCP 上可放大 |
| 写队列上限 | 256 | 16 – 1024 | 高延迟链路（BLE）下调小 |
| 防重放窗口 | 64 | 16 – 256 | 链路乱序严重时调大 |
| 握手超时 | 12 s | 5 – 30 s | 慢链路上调大 |

**不可调**：KDF 迭代下限、tag 长度、nonce 长度、AAD 内容、加密开关的默认值。

## 5. 如何测量（不要凭感觉优化）

### 5.1 已有埋点

`CbbSecurityLog`（Windows `%APPDATA%\ClipSync\security.log`，Android `getExternalFilesDir()/security.log`）已经记录：

- `negotiate: probe sent` / `peer is legacy`
- `handshake: HELLO suite=… kdf=…` / `CHALLENGE sent` / `READY, encrypted`
- `drop: replay/out-of-window seq=…` / `drop: tag mismatch (count=…)` / `drop: plaintext frame inside encrypted session`
- `SECURITY-FAILED: <reason>`

统一前缀便于 `grep`。日志 2 MB（Win）/ 512 KB（Android）轮转。

### 5.2 建议补的计时点

若要量化，加三个只进日志的时间差（Release 也保留，仅毫秒级整数）：

| 点 | 含义 | 期望 |
|---|---|---|
| `t_probe → t_hello` | 协商耗时 | < 50 ms |
| `t_hello → t_ready` | 握手耗时（含 PBKDF2） | 50–300 ms |
| 每帧 `t_seal` / `t_open` | 单帧加解密耗时 | < 100 µs（1 KiB） |

### 5.3 压测方法

| 用例 | 方法 | 通过标准 |
|---|---|---|
| 吞吐 | 连续发 1000 条 4 KiB 消息 | 无丢帧、无 tag 失败、吞吐接近链路裸速 |
| 大帧 | 单条 8 MiB | 完成、内存峰值可接受、无 OOM |
| 长稳 | 连续 8 小时每分钟 1 条 | 无内存增长、无序号异常 |
| 弱网/抖断 | 传输中途强制断开 100 次 | 每次都能在 12 s 内清理，无残留会话 |
| 恶意注入 | 随机字节灌入 | 全部 `bad-header` 断开，不崩、不越界 |

## 6. 性能优化时的安全红线

| 红线 | 原因 |
|---|---|
| 不得为提速跳过 tag 校验 | 等于删除完整性保护 |
| 不得为提速复用 nonce | GCM 下 nonce 复用直接泄露明文异或值并可伪造 |
| 不得为提速改用 ECB / 无认证模式 | 结构性缺陷 |
| 不得为提速降低 KDF 迭代到 10 000 以下 | 降低离线爆破成本（代码里已夹紧） |
| 不得为提速关闭防重放窗口 | 重放攻击重新可行 |
| 不得为提速把解密放到多线程乱序执行 | 破坏 seq 单调判定 |
| 不得为提速在 Release 打开明文日志 | 明文落盘 = 加密白做 |

一句话：**性能可以让链路更快，安全不能让链路可信度变低。** 任何优化都必须先跑一遍自检 12/12 再谈收益。

## 7. 未来场景速查

| 场景 | 该做什么 | 不该做什么 |
|---|---|---|
| 剪贴板偶尔传 10 MB 图片 | 上层分片（§3.1） | 抬高 `MaxBody` 到 100 MiB |
| 迁移到 BLE（吞吐更低） | 调小写队列、调大握手超时（文档 05 §2.4） | 关加密换速度 |
| 低端设备握手慢 | 会话内复用派生结果；考虑 Argon2id 新套件 | 降迭代数到 1 000 |
| 要支持多人协同（多会话） | 每会话独立 `SecureChannel` + 独立密钥 | 多会话共享密钥/序号 |
| CPU 占用成为瓶颈 | 检查是否走硬件 AES；考虑 ChaCha20 | 换 ECB / 关认证 |
