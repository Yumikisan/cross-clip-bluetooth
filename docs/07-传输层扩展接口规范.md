# 07 · 传输层扩展接口规范

> 适用版本：2.4.0 起（Android `transport/`、Windows `Services/Transport/`）
> 目的：把「怎么传字节」与「传什么」彻底分开。新增传输链路（BR/EDR 高速通道 HDT、局域网 TCP、BLE L2CAP）**只写一个连接器**，不改剪贴同步、文件队列、BFS 文件夹传输的任何一行。

## 1. 分层位置

```
socket / stream
   ↓  ← 只有这一层随链路变化
TransportLink（字节 / 帧）
   ↓
SecureChannel（探针协商、PSK、AES-256-GCM、seq 与 64 帧滑窗）
   ↓
Wire（一行一 JSON）
   ↓
剪贴同步 / 单文件队列 / 文件夹 BFS / 历史 / 通知
```

**PSK 层在契约之上**，不随链路变化：无论新链路自带链路加密（Secure RFCOMM、TLS）与否，二层保护一模一样。这是故意的——新链路不能成为「少一层加密」的后门。

## 2. 契约清单

| 类型 | 位置（安卓 / Windows） | 职责 |
| --- | --- | --- |
| `TransportKind` / `TransportKindIds` | `transport/Transport.kt` / `TransportContracts.cs` | 链路枚举与稳定 id（`rfcomm`、`lan-tcp`、`ble-l2cap`、`hdt`），用于设置、日志、诊断页 |
| `TransportCapabilities` | 同上 | 后端能力：单次写入上限、能否拨/听、链路加密、估算吞吐、是否支持发现 |
| `TransportPeer` | 同上 | 对端身份：`id`（唯一可信标识）、显示名、kind、入站标记 |
| `TransportLink` / `IPeerLink` | 同上 | **业务层唯一可见的接口**：`send`/`sendFrame`、`close`、`isOpen`、`isAuthenticated`、`isEncrypted`、`isLegacyPeer`、`rttMs`、`throughput`、`lastActivity`、`securityFailure`、`peer`、`capabilities` |
| `TransportConnector` / `ITransportConnector` | 同上 | 单后端的开链入口：`canHandle`、`isAvailable`、`connect`、`lastError` |
| `TransportRegistry` | `transport/TransportRegistry.kt` / `Services/Transport/TransportRegistry.cs` | 注册与选择：按 kind + 可用性 + 偏好顺序给出候选连接器 |
| `RfcommConnector` | 同上 | 当前唯一实现，仅把既有 RFCOMM 管理器包成契约面 |

安卓已有实现：`BtLink : TransportLink`（`bluetooth/BtLink.kt`），注册在 `BluetoothService.registerTransports()`。
Windows 已有实现：`PeerSession : IPeerLink`（`Services/BluetoothLinkManager.cs`），注册在 `BluetoothLinkManager` 构造器；契约入口 `OpenLinkAsync(TransportPeer, timeoutMs, token)`。

## 3. 新增一条链路要做的事（以局域网 TCP 为例）

1. 写 `LanTcpConnector : ITransportConnector`
   - `Kind = TransportKind.LanTcp`
   - `CanHandle(peer)`：`peer.kind == LanTcp && peer.id` 形如 `host:port`
   - `IsAvailable()`：Wi-Fi/以太网在线（拿不到就返回 false，**绝不返回 true 赌一把**）
   - `ConnectAsync(peer, timeout)`：建 TCP → 交回一个 `IPeerLink` 适配器（内部仍是 `SecureChannel(stream)`）
2. 适配器只需实现字节读写：Windows 复用现成的 `RfcommTransport(Stream, label)`（它对任何 `Stream` 都成立）；安卓照 `RfcommTransport` 再写一个 `StreamTransport`（换 `Socket` 的输入输出流）。
3. 在管理器里 `Transports.Register(new LanTcpConnector(...))`。
4. 设置页只显示 `Transports.ImplementedKinds()` 里有的通道，**没有连接器的链路不能出现在界面上**（否则开关存在但不起作用）。
5. 跑契约自检：Windows `CBB.exe --selftest` 的 `transport-contract` 项、安卓 `:app:testDebugUnitTest` 的 `TransportRegistryTest`。

**不需要动的地方**（这就是契约的意义）：剪贴发送/接收、文件队列与大小上限、BFS 文件夹遍历与 `folder_begin/mkdir/file_end/folder_end`、CRC 与 `.cbbpart` 原子改名、历史与通知、安全策略与握手。

## 4. 硬性约束（任何新后端都必须满足）

1. **可靠有序字节流**：`read` 返回 ≤0 表示对端关闭；不允许丢帧乱序（要自己在上层做重传的链路不适合直接接进来）。
2. **单次写入切片**：超过 `Capabilities.MaxWriteBytes`（RFCOMM 取 4096 B）必须由适配器切分；多 KB 单次写入在部分协议栈上会被截断。
3. **`send` 返回 false 即视为链路已死**：调用方只会当失败处理，不会重试同一条链路。
4. **`peer.id` 稳定且唯一**：断线重连后必须还是同一个值，仲裁、去重、历史归属全依赖它。
5. **不能绕过 SecureChannel**：任何新后端都从字节层接入，直接收发业务 JSON 视为破坏加密保证。
6. **不新增业务开关**：新链路的启用与否属于「传输通道」设置分组，不进剪贴/文件开关体系。

## 5. 仲裁与多链路

- 现有 RFCOMM 仲裁规则（两端都能拨，按「发起方 node id 较小者胜出」去重）留在 RFCOMM 管理器内，**不上升为通用规则**：局域网 TCP 只有一端监听，不需要同样机制。
- `TransportRegistry.Candidates(peer)` 按 `TransportContract.Preference` 排序（`HDT > LAN_TCP > BLE_L2CAP > RFCOMM`）。同一个对端同时可达多条链路时，由注册表给出顺序，业务层不参与选择。
- 现阶段 `Preference` 只影响排序，不改变行为：只有 RFCOMM 一个连接器。

## 6. 版本与兼容

- `TransportContract.Version = 1`，只在 `TransportLink`/`IPeerLink` **形状变化**时递增。
- `TransportContract.Implemented` 必须与实际注册的后端一致；自检会断言两者不漂移。
- 新增后端不得改变既有 RFCOMM 的 `Wire` 行为与安全握手，否则旧版对端会被拒（旧版只认 RFCOMM）。

## 7. 验收清单（新链路合并前逐条过）

- [ ] `--selftest` 全绿（含 `transport-contract`）
- [ ] `TransportRegistryTest` 全绿
- [ ] 新后端未出现在「未实现」状态下（`ImplementedKinds()` 与注册一致）
- [ ] 断链后 `send` 立即返回 false，不出现「假连接」
- [ ] 剪贴、单文件、文件夹（含空目录、深层目录、CRC 校验）三项在新链路各跑通一次
- [ ] 关掉新链路开关后，业务回到 RFCOMM，无残留连接
