# Cross Clip Bluetooth — 2.6.0 (Windows 2.5.0)

**这是一次身份变更**：本版起 Cross Clip 使用自己的 `applicationId`，因此可以和官方 ClipSync **同时安装、同时使用**，不再需要先卸载对方。

## 为什么要改

原作者 **aubynsamuel** 在讨论区回复：

> Feel free to change the ID and the name. In fact, I suggest changing it, as it will make it easier to distinguish and will also allow both apps to be installed at the same time.

之前坚持沿用上游 `applicationId` 的理由是「改包名会导致无法覆盖安装、丢配置，收益为零」。现在这个前提变了：两个应用并存才是有价值的目标，所以按他的建议改了。

| 平台 | 文件 | 版本 |
| --- | --- | --- |
| Android 7.0+ | `CCB-Android-2.6.0.apk` | `versionCode 92` / `2.6.0`，`com.yumikisan.crossclip` |
| Windows 10/11 | `CCB-Windows-2.5.0.exe` | 自包含单文件，无需 .NET 运行时 |

## 改了什么

### 1. 安卓：独立 `applicationId`

`com.aubynsamuel.clipsync` → **`com.yumikisan.crossclip`**。

Manifest 里的 `${applicationId}.fileProvider` / `${applicationId}.shizuku` 都是占位符，自动跟随新 ID；Kotlin 包名与 `namespace` **保持不动**——它只负责给类命名，与安装标识无关，改它要动 348 处引用却换不来任何行为变化。

### 2. Windows：独立配置目录，且自动迁移

`%APPDATA%\ClipSync` → **`%APPDATA%\CrossClip`**。

首次启动时如果新目录不存在、旧目录存在，会**自动复制一份**过去——口令、历史、设置全部保留，不用重新配对。旧目录原样留着，官方版继续用自己的，两边互不干扰。

另外两项也一并改名，否则两个应用会互相抢：

- 单实例互斥名 → `Local\CrossClip.SingleInstance`
- 开机启动项注册表值名 → `Cross Clip`（旧的 `ClipSync` 在首次切换时被接管并删除，不会开机启动两份）

### 3. 蓝牙协议刻意不动

**RFCOMM UUID（`8ce255c0-200a-11e0-ac64-0800200c9a66`）与 `CBB-HS-*` / `CBB-MASTER-v1` / `CBB-KEY-*` / `ClipSync-SAS-v1` 协议标签全部保留。**

也就是说：Cross Clip 依然能和官方 ClipSync 互传剪贴板。分开的只是应用身份、配置目录和后台服务，不是协议。只有 SDP 记录名改成了 `Cross Clip`（仅显示名，不影响发现——发现靠 UUID）。

## 升级注意

- **安卓**：换了 `applicationId` 就读不到旧包的私有存储（`Android/data/<包名>/files`），因此会以**全新档案**启动，口令需要重新配一次。旧的 2.5.x 可以留着并存，也可以卸载。
- **Windows**：自动迁移，无需重配。
- **两个应用同时运行时**，只有一个能占用蓝牙 RFCOMM 监听。Windows 上后启动的那个会提示监听失败——这是 RFCOMM 的服务端特性，不是本版引入的问题。日常使用建议同一时间只开一个。
